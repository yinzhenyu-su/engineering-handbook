# 评测分类法

人们说“我们得做评测”的语气，跟说“我们得加监控”一模一样，好像这是同一件事。它不是。告诉你某个 prompt 改动能不能安全合并的评测，和告诉你检索器上周二悄悄坏掉的评测，完全不是一回事；而这两个又都不是那种告诉你真实用户到底有没有把活干完的评测。

四个问题，四种不同的工具。选错了，你会以很高的精度测错东西，然后得出“系统没问题”的结论，而它正在悄悄烧着。这套分类法就是四个维度，用来给每一次选择命名。花两分钟看懂地图，能省下几周搭错基础设施的时间。

四个维度彼此独立，按用例组合：

- **离线（offline）还是在线（online）。** 我是在部署前做测试，还是在盯线上流量？
- **组件（component）还是端到端（end-to-end）。** 我打分的是一条流水线里的某个阶段，还是最终输出？
- **有参考答案（reference-based）还是无参考答案（reference-free）。** 我手上有没有一条标准答案可以拿来对比？
- **自动评分（automatic）、评判者评分（judge）还是人工评分（human）。** 谁来打分？

接下来本章逐个走一遍这四个维度，给出决定它的那条规则，然后展示一套真实的评测体系怎么把这四个维度混起来用。

## 离线与在线：我是在测试，还是在盯线上？

离线评测在部署之前跑，用的是一份你自己掌控、精心整理的数据集。输入固定，运行可复现，在笔记本上能把整套评测重跑一百遍。这是 CI 的世界：回归套件卡住合并，基准数据集对比两个 prompt，回测拿上个月的轨迹（trace）跑今天的代码。

在线评测跑在真实的生产流量上：要么同步嵌在请求链路里（一道拦下坏输出的护栏），要么异步跑在抽样的轨迹上（一个标记回归的监控）。通常没有标准答案，因为没人为这个用户的问题写过一条。你只能用无参考答案的信号来衡量：评判者模型、点踩率、被放弃的会话。

两者谁也替代不了谁。它们回答的是不同问题：

- **离线**回答的是*“这个改动能不能安全上线？”* 快、便宜、可重复。数据集之外的东西它一样也看不见。
- **在线**回答的是*“线上系统现在还好吗？”* 能抓住真实分布和新出现的故障。没有真值，所以它依赖评判者，或者依赖你必须信任的代理信号。

默认规则：**先离线，等用户是真的了再上在线。** 开发期间先搭一个小规模的 CI 评测集（截至 2026 年 1 月，Hamel Husain 和 Shreya Shankar 建议一百条以上样本才算得上一个有意义的 CI 下限[^1]）。等生产流量跑起来、你需要捕捉离线集看不见的漂移时，再加在线评测——比如供应商端点背后的模型换了版本，或者冒出了一类新的查询模式。

陷阱在于把它们当成两套独立系统。它们是一个闭环。在线监控抓到的生产故障，会作为新的回归用例进入离线数据集，下一轮 CI 就永远挡得住这个具体故障。如果你的离线集从来不从生产数据里长出来，那它就是一座博物馆。

## 组件与端到端：我把评测对准哪里？

端到端评测把系统当成黑盒：给一个输入，给最终输出打分，结束。

组件评测单独瞄准某一个子系统：只测 RAG 流水线里的检索器，只测 agent 的工具选择步骤，只测多阶段工作流里的摘要器。检索器对一份标注好的查询—文档集算 Recall@k 这类信息检索指标；生成器做忠实性检查；工具选择器在一份标注好的“这里你会调哪个工具”数据集上算准确率。

端到端更简单，但它也掩盖了这颗星球上最常见的 RAG 故障：检索器返回一堆不相关的文档，生成器照样流利地编出一个看着像那么回事的答案，你的端到端分数纹丝不动，而检索其实已经在悄悄退化。生成器被训练成不管上下文窗口里装着什么都说得很有底气，它每次都会替坏掉的检索器打掩护。

组件评测存在的理由就在这里。Jason Liu 的“There Are Only 6 RAG Evals”框架（2025 年 5 月）把问题拆成三种可以独立测量的关系：给定查询的上下文（检索有没有找对东西？）、给定上下文的答案（模型有没有待在上下文里？）、给定查询的答案（答案有没有回应原问题？）。[^2] 端到端分数掉了，这三个组件分数会告诉你哪一段坏了。

默认规则：**先做端到端，立一条质量基线；等错误分析指向某个具体阶段，再上组件评测。** 唯一的例外就是 RAG：检索故障在统计上实在太常见，很多实践者干脆把规则反过来，直接从检索指标开始。只要你的系统里有检索器，第一天就把 [Recall@k](../part-6-retrieval-augmented-generation/07-evaluating-retrieval.md) 接上监控；跳过这一步只是把迟早要做的调试往后推。

对 agent 来说，分层版本是先看端到端的任务成功率（“agent 到底把用户的活干完了没有？”），再对失败的轨迹做步骤级诊断：哪个工具调用、哪次参数抽取、哪个状态转移出了问题。[^1] 每一项都是它自己的组件评测。

## 有参考答案与无参考答案：我手上有标准答案吗？

有参考答案的评测拿模型输出和一条已知正确的答案比：分类任务用完全匹配，字面重合用 ROUGE 或 BLEU，语义相似度用 BERTScore、COMET 这类学习型指标。好处是一旦参考答案就位，分数就是确定的、便宜的。

无参考答案的评测在没有标准答案的情况下打分。机制无非三种：一个读完问题和回答再判定质量的评判者模型；一次一致性自检（模型在不同次运行之间跟自己一致吗？）；或者一条领域相关的断言（回答里有没有带上客户的订单号？）。

对开放式 LLM 输出做有参考答案的评测，问题在于“参考答案”本身就是虚构的。Eugene Yan 在 2024 年 3 月记录了摘要任务上参考型指标的三处结构性缺陷：参考答案本身就是标注瓶颈；它们的质量可能还不如模型生成的东西（Fabbri 等 2021 与 Zhang 等 2024 都发现生成摘要在质量上压过了 CNN/DailyMail 的参考摘要）；可接受的答案之间差异太大，好输出和坏输出会落在互相重叠的分数区间里。[^3] 在 WMT23 里，排名前七的翻译指标中有四个是无参考答案的——这个领域在往哪走，一目了然。[^3]

Husain 说得更直接：BERTScore、ROUGE、余弦相似度这类通用的参考型指标“在大多数 AI 应用里对评估 LLM 输出没什么用”，只有一个例外——搜索与检索，在那里余弦相似度确实测到了有意义的东西。[^1]

决策规则比看上去要窄：

- **有参考答案**——当答案是有边界的：分类、抽取、数学、能编译的代码、能返回行的 SQL。参考答案就是真值，完全匹配就是评测。
- **无参考答案**——当输出是开放式的（摘要、对话、agent 轨迹），或者参考答案的质量会低于模型。

还有第三种常被忘掉的选项：即便是开放式任务，通常也存在可以直接写成代码的*确定性约束*。“回复里必须包含客户的订单号。”“JSON 必须能通过这个 schema 的校验。”“代码必须通过这些单元测试。”这既不是参考答案，也不是评判者，而是断言——而且它比两者都强。能写成规则，就写成规则。

## 自动评分、评判者评分还是人工评分：谁来打分？

这是成本梯度最陡、出错方式最多的一个维度。

**自动评分**是确定性的代码：正则、JSON schema 校验器、完全匹配比较器、代码执行检查。它们毫秒级跑完，单次评测的成本基本为零，100% 可复现。只要一件事能表达成对输出结构或内容的布尔判定，自动评分就是对的默认选择。

**LLM-as-judge** 用一个模型来打分：你写一段描述评分标准的 prompt，把问题和回答（可选再加一份参考答案）交给它，要一个判决。Lianmin Zheng 等人的 MT-Bench 论文（NeurIPS 2023）是这项技术的实证支点：在多轮开放式问题上，GPT-4 与人类专家的判断一致率超过 80%，与人类之间 81% 的一致率相当。[^4] 正因为这个结果，如今每个现代评测平台都要带一层评判者。OpenAI 的 Graders API（2025）把它固化成四种评分器：`string_check`、`text_similarity`、`score_model`（即 LLM-as-judge），以及用于任意领域逻辑的 Python 评分器。[^5]

**人工**评估是金标准，也是其他所有评估的校准锚点。一位领域专家读轨迹，带来任何自动评分器都说不出来的隐性知识，并定义对业务来说“好”到底是什么。Husain 的建议是任命一个“仁慈的独裁者”（由一位专家拍所有板），而不是把众包标注者的意见平均——他们之间的分歧只会添噪声。[^1] 成本是明摆着的问题：领域专家每条标注大约 1 美元，众包标注者约 0.08 美元，LLM 生成的标注不到 0.003 美元（单一来源估算，2026 年 4 月）。[^6]

成本差异之所以重要，是因为它逼你做分层决策。

![一架竖直的梯子，五档评测技术从最便宜排在底部到最贵排在顶部：最下面是断言，往上是文本匹配评分器，再往上是 LLM-as-judge，然后是人工评审，最顶部是 A/B 测试；一个很小的工程师人形站在 LLM-as-judge 这一档上，一支向上的箭头标着信号保真度，一支向下的箭头标着速度，梯子旁边一列逐渐增高的硬币堆显示成本在涨](../../../ai-eng/part-8-evaluation-and-observability/images/00-the-eval-cost-ladder.png)
*成本梯子决定了顺序：先上便宜的评估器，贵的只留给便宜评估器抓不住的失效模式。*

梯子上的顺序也是建设的顺序。从断言开始。表达不成布尔判定的失效模式，加一层评判者。人工评审留给校准评判者和高风险决策。只有当你需要知道某个质量提升有没有推动真实用户指标时，才上 A/B 测试。

评判者这一层正是这个维度变危险的地方：它感觉像自动评测，行为却像一个不靠谱的人。Zheng 等人量出了三种偏差，每一个不检查它们的团队都会中招。位置偏差：成对比较中，Claude-v1 有 75% 的情况偏爱第一个回答；在质量相近的样本对上，GPT-4 交换位置后判断保持一致的比例只有 65%（2023 年 6 月）。[^4] 冗长偏差：GPT-3.5 和 Claude-v1 都有 91.3% 的情况扛不住“重复列表”攻击，宁可要一个注水拉长的回答，也不要一个简洁正确的回答。[^4] 自我增强偏差：相比人类评估，GPT-4 给自己输出的胜率高出约 10 个百分点。[^4]

缓解办法是机械的：每个成对评测都跑两种顺序，只有同一个回答在两个方向上都胜出才算赢。优先用二值通过/不通过，而不是李克特量表——它逼你把标准写清楚，也能在更小的样本上测出回归。[^1] 在信任任何一个评判者之前，先拿至少 100 条人工标注样本验证它，测出它的真阳率和真阴率。两个指标都低于 80% 左右，就去改 prompt，或者换评判模型。[^1]

符合这条规则的评判者 prompt 很短，返回 JSON，而且只要求一个二值判决：

```python
import json

def build_judge_prompt(question: str, response: str, criterion: str) -> list[dict]:
    system = (
        "You are a strict quality evaluator. Respond only with a JSON object: "
        '{"pass": true|false, "reason": "..."}.'
    )
    user = (
        f"Criterion: {criterion}\n\n"
        f"Question: {question}\n\n"
        f"Response: {response}\n\n"
        "Does the response meet the criterion? Reply with JSON only."
    )
    return [{"role": "system", "content": system}, {"role": "user", "content": user}]

def parse_judge_output(raw: str) -> dict:
    try:
        return json.loads(raw.strip())
    except json.JSONDecodeError:
        return {"pass": False, "reason": "parse_error"}
```

这只是脚手架。难的不是代码，而是把标准写到足够具体——具体到两个人会就同一份输出给出同一个判决——以及在 prompt、模型或任务变动时重新验证评判者。Shankar 等人（UIST 2024）把背后的这个问题叫“标准漂移（criteria drift）”：用户需要标准才能给输出打分，但恰恰是打分的过程才让他们明白自己的标准到底是什么。[^7] 校准一次就永远信任的评判者，会在无人察觉中烂掉。

## 读图：哪种组合回答哪个问题

四个维度会组合起来。多数生产系统同时并行跑好几种组合，每一种对准不同的问题：

| 问题 | 离线 / 在线 | 组件 / 端到端 | 参考答案 | 评分者 |
|---|---|---|---|---|
| 这个 prompt 改动能不能安全合并？ | 离线 | 端到端 | 混合 | 自动 + 评判者 |
| 我的检索器是不是悄悄退化了？ | 离线 | 组件 | 有参考答案 | 自动（Recall@k） |
| 这一周用户还满意吗？ | 在线 | 端到端 | 无参考答案 | 评判者 + 隐式信号 |
| 新模型比旧模型好吗？ | 在线 | 端到端 | 无参考答案 | A/B 测试（人工，通过行为体现） |
| agent 选对工具了吗？ | 离线 | 组件 | 有参考答案 | 自动（完全匹配） |
| 我们在生产里出幻觉了吗？ | 在线 | 组件（忠实性） | 无参考答案 | 评判者 |

每一行都是一个不同的基础设施决策。第一行的 CI 门禁是一个几秒钟跑完的 Python 脚本；倒数第二行的答案却是要切流量、算统计功效、跑好几周的实验。把两者混为一谈，就是有些团队在 CI 里跑 LLM-as-judge（慢，每次合并都贵），或者想拿 A/B 测试卡部署（慢到不可能）的原因。分类法是地图，上面这些行是路线。

地图没画出来、而这一部分后面每一章都会强调的一点是：这些东西都要在错误分析之后才建。Husain 和 Shankar 教过两千多名工程师得出的经验数字是，AI 产品开发时间里有 60% 到 80% 应该花在错误分析和评测上（截至 2026 年 1 月）。[^1] 你要先读轨迹，把失败聚成类，*然后*再决定哪些维度组合真正能回答你团队眼下没答案的问题。脱离具体问题去搭评测基础设施，只会得到对错误对象的高精度测量。

放到架构尺度上，[AI 系统的评测与可观测性](../../hld/part-9-ai-ml-system-design/05-llm-evaluation-observability.md)从轨迹埋点和指标管道的角度讲了同一个问题。后面几章分别深入这张地图上的具体格子：[LLM-as-judge](./01-llm-as-judge.md)讲怎么建一个你能信任的评判者，[评判者的失效模式](./02-judge-failure-modes.md)讲偏差的缓解办法，[评测 RAG 与 agent](./03-evaluating-rag-and-agents.md)讲组件评测的套路，[在线评测与 A/B 测试](../../../ai-eng/part-8-evaluation-and-observability/05-online-evaluation-and-ab-testing.md)讲线上流量这一侧在生产里实际长什么样。
